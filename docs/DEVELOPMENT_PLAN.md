# Vedara Longevita — анализ репозитория и план развития

Дата: июнь 2026. Документ фиксирует текущее состояние MVP и дорожную карту до продуктовой версии.
Связанный документ: [BACKEND_SPEC.md](./BACKEND_SPEC.md) — техническое задание на backend.

---

## 1. Текущее состояние репозитория

### Что уже есть

- **Работающий mobile-first демо-продукт**: React 19 + TypeScript 5.8 + Vite 7, без роутера и UI-фреймворков. Шесть экранов (`home | practices | tracker | club | chat | profile`), hash-навигация, жест «свайп назад» (`useEdgeSwipeBack`).
- **Чистая архитектура контента**: весь текст и структуры вынесены в `src/data/content.ts` (сгруппирован по экранам, в шапке — маппинг на будущие backend-ресурсы). Типы централизованы в `src/data/types.ts`.
- **Модель состояния пользователя** уже спроектирована и живёт в `localStorage` (9 ключей `vedara.*` в `App.tsx`): доступ/тариф, ежедневные чек-ины, привычки, прогресс по материалам/протоколам/клубным видео и статьям, заявки (leads), интересы к продуктам.
- **Домены-заглушки**: подписка (5 555 ₽/мес, trial 7 дней), заявки в Clinic/University/диагностику/индивидуальный протокол — всё мокировано, реальных платежей и сети нет.
- **Recovery Score™** (`src/utils/recovery.ts`) — индекс ресурса 0–100 из чек-ина; это ядро будущей продуктовой аналитики.
- **Дизайн-система**: токены в `src/styles/tokens.css`, направление «Editorial Light» + Liquid Glass на хроме, линтер запрета сырых hex (`lint:colors`).
- **Много документации** в `docs/` (23 файла: скоуп, стайлгайд, пейволл, чек-листы QA).

### Технический долг и риски

| # | Проблема | Влияние |
|---|---|---|
| 1 | **Легаси-код**: `src/screens/` не импортируется; `src/styles/components.css`, `global.css` не загружаются; `src/data/{materials,products,programs,progress,services}.ts` частично дублируют старую модель | Путает новых разработчиков и ИИ-агентов; риск правок «не туда» |
| 2 | **Устаревшие доки**: `docs/DATA_MODEL.md` описывает старую модель `wellness-mvp-state-v1`, не соответствующую коду | Ложный источник правды |

## 2. План развития

Этапы упорядочены так, чтобы каждый давал самостоятельную ценность. Оценки — в неделях работы 1–2 разработчиков.

### Этап 0 — Гигиена репозитория (~1 неделя, можно параллельно с чем угодно)

- Удалить легаси: `src/screens/`, неиспользуемые CSS, устаревшие data-файлы (после проверки импортов).
- Актуализировать/удалить устаревшие доки (`DATA_MODEL.md` и пр.), оставить `CLAUDE.md` источником правды.
- Сжать/даунскейлить ассеты (логотип 18 МБ → WebP ≤200 КБ), добавить бюджет размера в CI.
- Ввести ESLint + Prettier, unit-тесты (Vitest) на `recovery.ts` и storage-хелперы.
- GitHub Actions: `typecheck + lint + test + build` на каждый PR; деплой только с зелёного билда.

### Этап 1 — Продуктовая полировка демо (GOAL 002–003, 2–3 недели)

- Финализировать копирайт и лицензированные фото с клиентом.
- Дожать «мёртвые» участки: прогресс клубных статей, детальные страницы уроков, видео-плейсхолдеры.
- Режим презентации: сброс демо (уже есть) + сид демо-данных «за 2 недели» для красивого трекера.
- PWA-минимум: manifest, иконки, установка на домашний экран (задел под GOAL 007).

### Этап 2 — Backend: аккаунты и синхронизация (GOAL 004, 4–6 недель)

Ядро этапа — по ТЗ в [BACKEND_SPEC.md](./BACKEND_SPEC.md):

- Аутентификация (OTP по телефону/email), профиль.
- Серверное хранение всего, что сейчас в `localStorage`: чек-ины, привычки, прогресс, заявки, интересы; статус подписки как server-side source of truth.
- Выдача контента через API/CMS вместо `content.ts` (поэтапно: сначала user-state, затем контент).
- Миграция: одноразовый импорт `localStorage` в аккаунт при первом входе.
- На фронте — тонкий API-слой (`src/api/`), офлайн-очередь записи, оптимистичные обновления; структура экранов не меняется.

### Этап 3 — Платежи (GOAL 005, 3–4 недели, после этапа 2)

- Провайдер: ЮKassa или CloudPayments (рынок РФ, рекуррентные списания).
- Server-side checkout, вебхуки, продление/отмена, trial 7 дней, отзыв доступа.
- Юридический контур: оферта, политика ПДн (152-ФЗ — чек-ины близки к данным о здоровье), чеки (54-ФЗ).

### Этап 4 — Заявки и админка (GOAL 006, 2–3 недели, частично параллельно этапу 3)

- Формы заявок Clinic/University/диагностика/протокол → CRM-подобная админка (или интеграция: Telegram-уведомления + amoCRM/Bitrix24).
- Статусы заявок в приложении (`/me/leads`).
- Минимальная контент-админка (CMS): редактирование уроков, видео, копирайта без релиза фронта.

### Этап 5 — Живой клуб (после запуска базы)

- Реальный чат/сообщество (сейчас экран-заглушка): либо своя реализация на WebSocket, либо интеграция (Telegram-канал / Getcourse / Circle).
- Видео-хостинг для клубного контента (Kinescope/Boomstream — рынок РФ) с защитой ссылок.
- Push-уведомления (PWA Web Push): напоминание о чек-ине, новые материалы.
- Аналитика продукта (ретеншн чек-инов, воронка trial→подписка).

### Этап 6 — Нативная упаковка (GOAL 007, по мере спроса)

- Capacitor-обёртка поверх PWA → App Store / Google Play, когда подтверждён спрос.

### Сводная последовательность

```
Этап 0 (гигиена) ──┐
Этап 1 (полировка) ─┼─→ Этап 2 (backend/auth) ─→ Этап 3 (платежи) ─→ Этап 5 (клуб) ─→ Этап 6 (натив)
                    └────────────────────────────→ Этап 4 (заявки/админка)
```

Ключевая веха «продукт, а не демо» = конец этапа 3: аккаунты + синхронизация + реальная подписка.

## 3. Принципы на всём пути

- **Фронт остаётся тонким**: экраны и дизайн-система не переписываются; меняется только источник данных (`localStorage` → API) через изолированный слой.
- **Контент — в CMS, состояние — в БД**: граница уже проведена в коде (`content.ts` vs `App.tsx` state), backend обязан её сохранить.
- **Каждый этап демонстрируем клиенту**: ветка `vedara-mvp` остаётся всегда-зелёным демо; интеграционные работы идут в фиче-ветках за фиче-флагами.
- **Данные о самочувствии = чувствительные данные**: минимизация сбора, шифрование, российский хостинг ПДн.
